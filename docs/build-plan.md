# 하루 파일럿 구현 진행안 (팀 제안안)

**상태**: 팀 제안안 — 팀 회의에서 확정 전 · **작성일**: 2026-11-27
**관련 문서**: [시스템 구조](system-architecture.md) · [데이터 모델](data-model.md) · [하루 파일럿 설계 전 검토](pilot-design-review.md)

[시스템 구조](system-architecture.md)를 하루(8시간) 안에 어떤 순서로, 누가 무엇을 맡아 만들지 정리한 안이다. 아래 내용은 모두 **팀에 제안하는 안**이며 팀의 결정이 아니다.

## 1. 요약

- 백엔드와 처방 추천 에이전트는 **FastAPI 프로세스 하나**에서 돌린다. 코드는 패키지로 나눈다.
- 에이전트 도구는 백엔드 REST API를 호출하지 않고, **API 라우터와 같은 서비스 함수**를 호출한다.
- 먼저 **계약(인터페이스)을 고정하고, 더미 구현으로 끝까지 이어지는 흐름**(백엔드·에이전트·프론트엔드)을 만든다.
- 더미를 만드는 동안 다른 팀원은 **비전 인식, 판단 알고리즘, RAG**를 테스트하고 확정한다. 확정된 구현은 더미와 바꿔 끼운다.
- 더미 골격은 **토픽 7개**(GitHub 이슈 #2~#8)로 나눠 진행한다. 병행 트랙의 계약을 담은 T1을 가장 먼저 끝낸다 (7절).

## 2. 실행 구조

### 2-1. 백엔드와 에이전트를 한 프로세스로

[시스템 구조](system-architecture.md) 1절의 전제(대표자 PC 한 대, 프로세스 하나)를 그대로 따른다.

| 얻는 것 | 내용 |
| --- | --- |
| 실행이 단순하다 | `uvicorn` 하나로 API, 분석 작업, 에이전트, SSE가 모두 뜬다. 포트·프로세스 간 통신·서비스 사이 인증이 없다. |
| 이벤트를 바로 공유한다 | 대화 중 추천 카드가 고쳐지면 같은 이벤트 버스로 화면에 바로 알린다. |
| 리셋이 쉽다 | `app.db`·`checkpoints.db`를 새로 만들고 시드를 다시 넣으면 끝난다. |

한 프로세스로 두더라도 다음은 지킨다.

- **코드 분리**: 에이전트 코드는 `recommender/` 패키지에 둔다. API 라우터에 섞지 않는다. 담당자가 다를 수 있고, 서버 없이 도구를 테스트해야 하기 때문이다.
- **비동기 실행**: 추천 생성과 대화는 수 초에서 수십 초가 걸린다. 에이전트는 `ainvoke`·`astream`으로 돌려 업로드와 SSE를 막지 않는다. 추천 생성은 분석 작업 실행기의 백그라운드 작업에서 돌리고 동시 실행 수를 제한한다.
- **실패 격리**: 에이전트 예외는 `recommender/` 경계에서 잡는다. 추천 생성 실패는 `recommendations.status = failed`로 남기고 사진 처리는 `done`으로 끝낸다 ([시스템 구조](system-architecture.md) 12절).
- **저장소 분리**: 체크포인터는 지금처럼 `checkpoints.db`에 따로 둔다. SQLite 쓰기 잠금이 업무 DB와 겹치지 않게 한다.

### 2-2. 에이전트 도구는 서비스 함수를 호출한다

에이전트가 DB를 직접 건드리지 않고 백엔드의 계약을 거친다는 방향은 같다. 그 통로를 REST 호출이 아니라 **함수 호출**로 한다.

```
api/ 라우터 ─────┐
                 ├─→ services/ ─→ storage/ (SQLite, 사진 폴더)
recommender/ ────┘
  (PatientDataPort Protocol에만 의존)
```

**REST 호출 대신 함수 공유를 제안하는 이유**

| 항목 | REST 호출 | 서비스 함수 공유 |
| --- | --- | --- |
| 호출 경로 | 같은 프로세스가 자기 자신에게 HTTP 요청. 주소 설정, 직렬화, HTTP 오류 변환이 늘어난다. | 함수 호출 |
| 서버 멈춤 위험 | 비동기 서버 안에서 동기 HTTP로 자기 서버를 부르면 워커가 막힌다. 도구를 모두 비동기로 만들어야 한다. | 없음 |
| 데이터 모양 | 화면용 API는 일별 합계만 준다. "자주 남긴 메뉴" 같은 에이전트용 요약은 엔드포인트를 따로 만들어야 한다. | 에이전트에 맞는 함수를 둔다 |
| 쓰기 주체 | `PATCH /api/recommendations/{id}`는 `last_modified_by = "doctor"`로 기록한다. 에이전트용(`agent`/`chat`, `thread_id`) 엔드포인트가 따로 필요하고, 접근 제어가 없으니 브라우저에도 열린다. | 쓰기 함수가 고친 주체를 인자로 받는다 |
| 규칙의 위치 | 라우터와 에이전트 전용 엔드포인트에 검증·이벤트 발행이 나뉠 수 있다. | 검증·상태 전이·이벤트 발행이 서비스 함수 한 곳에 있다 |
| 테스트 | 서버를 띄우거나 ASGI 클라이언트가 필요하다 | 함수와 가짜 구현으로 테스트한다 |

**REST가 나은 경우**: 에이전트를 별도 프로세스·서비스로 띄울 때, 다른 언어나 다른 팀이 만들 때, 인증·인가로 에이전트의 접근 범위를 제한해야 할 때(운영 단계). 파일럿에는 해당하지 않는다. 나중에 분리가 필요하면 `PatientDataPort`의 HTTP 구현을 만들어 바꿔 끼운다.

**`PatientDataPort` (후보)**

| 함수 | 하는 일 | 대응하는 도구 |
| --- | --- | --- |
| `get_intake_summary(patient_id, days)` | 최근 섭취 추이, 경고 수준, 자주 남긴 메뉴 | `get_intake_summary(days)` |
| `get_recommendation(patient_id)` | 현재 추천 카드 | 대화에서 카드 읽기 |
| `update_recommendation(recommendation_id, items, modified_by, thread_id)` | 추천 항목 수정. `modified_by`는 `agent` / `chat` / `doctor`. `recommendation.updated` 이벤트 발행 | `draft_prescription(items)` |

- 도구는 요청마다 선택한 환자 ID를 미리 묶어서 만든다 ([시스템 구조](system-architecture.md) 7절). 모델은 환자 ID를 인자로 고르지 않는다.
- 이벤트 발행은 서비스 함수가 맡는다. 화면에서 고치든 대화에서 고치든 같은 이벤트가 나간다.
- `services/` 패키지는 [시스템 구조](system-architecture.md) 11절 코드 구성에 더하는 항목이다.

## 3. 더미 우선 골격

### 3-1. 더미를 두는 위치

```
frontend (실제) → api/ 라우터 (실제) → services/ · IntakeEstimator · 에이전트 · 가이드라인 검색
                                         ↑ 여기를 더미로 시작해 실제 구현으로 바꾼다
```

- 라우터, 요청·응답 스키마, SSE 이벤트는 **처음부터 실제로** 만든다. 라우터를 더미로 만들면 나중에 다시 짜야 하고 응답 모양이 바뀔 위험이 있다.
- 그 아래 구현만 바꿔 끼우므로, 교체할 때 프론트엔드는 바뀌지 않는다.
- 프론트엔드는 FastAPI가 만드는 OpenAPI 문서에서 타입을 뽑아 쓴다.

### 3-2. 더미 목록

| 대상 | 더미 | 바꿔 끼울 실제 구현 |
| --- | --- | --- |
| 섭취 추정 | `FakeEstimator`: 정해진 비율을 돌려주고 판단 불가 칸·품질 문제를 섞는다. `estimate_basis = "vlm:fake"` | VLM 어댑터 (비전 트랙) |
| 영양 계산·경고 | 고정값을 돌려주는 함수 | 순수 함수 구현 (판단 알고리즘 트랙) |
| 가이드라인 검색 | 고정 구절 2~3개를 돌려주는 `FakeGuidelineSearch` | BM25 또는 임베딩 검색 (RAG 트랙) |
| 에이전트 (화면용) | `FakeAgent`: LLM 없이 고정 추천 카드와 고정 토큰 스트림, 도구 호출 이벤트를 보낸다 | 실제 `create_agent` |
| 에이전트 (기술 위험 확인용) | 실제 `create_agent` + 더미 도구 | 실제 도구 |
| 데이터 접근 | 처음부터 SQLite와 시드(`data/seed/demo_seed.json`) | — |

- 더미에도 **지연(2~5초)과 실패 경우**를 넣는다. 처리 상태 화면(④)과 실패 처리 화면을 더미 단계에서 확인하기 위함이다.
- 구현 선택은 설정값으로 바꾼다. 예: `INTAKE_ADAPTER=fake|<vlm 이름>`, `GUIDELINE_SEARCH=fake|bm25`, `AGENT=fake|real`. 시연 중 실제 연동이 실패하면 더미로 되돌려 흐름을 보여줄 수 있다.

## 4. 병행 트랙과 계약

### 4-1. 트랙별 계약

더미를 만드는 쪽이 **작업 첫 시간 안에** 계약을 코드로 고정해 공유한다. 세 트랙은 그 계약에 맞는 실제 구현을 가져온다.

| 트랙 | 넘겨줄 계약 | 받아올 것 |
| --- | --- | --- |
| **비전 인식** | `IntakeEstimator.estimate(EstimationRequest) -> EstimationResult` ([시스템 구조](system-architecture.md) 5절) | ① VLM 어댑터 클래스 ② 선정한 모델과 반복 호출 여부 ③ 저울 실측 식판 평가 결과(대략의 오차) |
| **판단 알고리즘** | `meal_nutrients`, `daily_target`, `daily_intake`, `evaluate_alert`의 시그니처와 입력 레코드 타입 ([시스템 구조](system-architecture.md) 6절) | ① 순수 함수 구현과 경계값 테스트 ② 임계값·기간 설정값 |
| **RAG** | `search_guidelines(query) -> list[GuidelineHit]` (`doc_id`, `section`, `text`, `source_url`) | ① 검색 구현 ② 문서 분할 결과와 색인 생성 스크립트 ③ 확인용 질의와 기대 근거 몇 개 |

- 세 트랙 모두 **DB를 몰라도 되게** 한다. 입력과 출력은 frozen dataclass로 주고받는다. 각 트랙은 서버 없이 단독으로 테스트한다.
- 계약 파일 후보: `intake/types.py`, `nutrition/types.py`, `recommender/guideline_types.py`, `services/ports.py`.

### 4-2. 계약 테스트

Fake와 실제 구현이 **같은 테스트**를 통과하면 바꿔 끼울 수 있다고 본다. 더미 쪽이 계약 파일과 함께 커밋한다.

| 대상 | 계약 테스트 예시 |
| --- | --- |
| 섭취 추정 | 요청한 칸이 결과에 빠짐없이 한 번씩 있다. 섭취 비율은 0~1, 0.1 단위다. 판단 불가 칸은 비율이 `None`이다. `estimate_basis`가 `vlm:`으로 시작한다. |
| 판단 알고리즘 | 경고 수준은 `none` / `caution` / `warning` 중 하나다. 판단 불가 칸은 합계에서 빠지고 `incomplete`가 켜진다. 기록된 끼니가 없는 날의 하루 %는 NULL이다. |
| 가이드라인 검색 | 결과 수가 상한 이하다. 모든 결과에 `doc_id`와 `source_url`이 있다. |

### 4-3. 트랙 사이에 맞출 것

- **계약을 바꿀 때는 먼저 공유한다.** 테스트하다가 출력 필드를 늘리거나 바꿔야 하면 계약 파일부터 고치고 알린다. 혼자 바꾸면 교체 시점에 프론트엔드까지 깨진다.
- **섭취 비율의 의미**: 판단 불가 칸을 `None`으로 넘기고 합계에서 빼는 규칙(`incomplete`)을 비전 트랙과 판단 알고리즘 트랙이 같이 이해한다 ([데이터 모델](data-model.md) 4절).
- **검색 결과의 크기**: RAG 결과는 에이전트 도구로 들어간다. 결과 수와 본문 길이를 에이전트 담당과 맞춘다. 너무 길면 프롬프트 비용과 응답 시간이 늘어난다.

## 5. 일정 (8시간 기준 예시)

| 시점 | 더미·통합 담당 | 병행 트랙 |
| --- | --- | --- |
| 시작 ~ 1시간 | 계약 파일·계약 테스트·Fake 구현 커밋, API 스키마 초안 | 계약 검토, 입출력 합의 |
| ~ 오전 끝 | 백엔드 라우터·SSE·더미 흐름, 프론트엔드 화면 작업 시작 | 각자 테스트. VLM 한 쌍 호출 확인, `create_agent` 기술 위험 확인 |
| 오전 끝 | **중간 점검**: 트랙별로 될 것·안 될 것, 계약 변경 필요 여부 공유 | |
| 오후 초 ~ | 화면 마무리, 교체 받아 통합 | 판단 알고리즘 → RAG → VLM 순서로 교체 |
| 마감 2시간 전 | **교체 중단.** 실제 구현이 안 된 부분은 더미로 두고 시연 리허설 | |

## 6. 교체 순서

1. **판단 알고리즘**: 외부 호출이 없는 순수 함수라 가장 빨리 끝난다. 경고·추천 흐름이 실제 시드 이력으로 움직이기 시작한다.
2. **RAG**: `FakeGuidelineSearch`를 실제 검색으로 바꾼다. 에이전트 답변의 근거가 실제 문서가 된다.
3. **섭취 추정**: `FakeEstimator`를 선정한 VLM 어댑터로 바꾼다.
4. **에이전트**: 더미 도구를 실제 서비스 함수로 바꾸고, 마지막으로 `FakeAgent`를 실제 에이전트로 바꾼다.

교체할 때마다 계약 테스트와 업로드부터 처방 확정까지의 흐름을 한 번 돌려 본다.

- 이슈 본문은 목표, 범위, 완료 기준 체크리스트, 선행 이슈, 참고 문서 순서로 적었다. 담당자는 팀 회의에서 배정한다.

### 7-2. 순서와 병렬 진행

```
T1 ─→ T2 ─┬→ T3 ───────────────┐
          └→ T4 ─→ T5 ─────────┤
T1 ─→ T6 ──────────────────────┴→ T7
```

- **T1을 가장 먼저 끝낸다.** 계약이 나와야 비전 인식·판단 알고리즘·RAG 트랙이 시작할 수 있다. 그래서 T1에는 서버 기능을 넣지 않고 작게 유지한다.
- **프론트엔드는 따로 간다.** 담당자가 있으면 T6은 T1 직후부터 백엔드와 동시에 진행할 수 있다.
- **나누는 기준**: 토픽마다 PR 하나로 리뷰할 수 있는 크기로 한다. T3과 T4는 화면이 쓰는 API 묶음으로 나눴다.

### 7-3. 고려할 점

- **진행 비용**: 토픽마다 spec → plan → impl → review → PR을 거친다. 하루 일정에서는 7개도 부담이 될 수 있다. 시간이 빠듯하면 T3+T4, T6+T7을 합쳐 5개로 줄인다.
- **커밋 스코프**: `.harness/commit-scopes.md`가 아직 기획안 기준(vision, MLP 등)이다. `recommender`, `events`, `jobs` 같은 스코프가 없으므로 구현에 들어가기 전에 함께 정리한다.

## 8. 위험과 대응

| 위험 | 대응 |
| --- | --- |
| 더미로 흐름이 돌아 실제 연동 시작이 늦어진다 | VLM 호출과 `create_agent` 기술 위험 확인은 더미 작업과 동시에 오전에 한다. |
| 더미와 실제 구현의 출력 모양이 다르다 | 계약 파일과 계약 테스트를 먼저 커밋하고, 실제 구현도 같은 테스트를 통과해야 교체한다. |
| 화면 작업이 일정의 병목이다 | 라우터와 스키마를 오전에 고정해 프론트엔드가 첫 시간부터 진짜 API로 작업한다. 먼저 끝난 트랙 담당이 화면 일부를 맡는다. |
| 시연 중 외부 API(VLM, Claude)가 실패한다 | 설정값으로 더미로 되돌린다. 시연 화면에 `estimate_basis`가 드러나므로 더미 결과임을 밝힐 수 있다. |

## 9. 팀이 정할 것

1. **담당자 배정**: 더미·통합(백엔드·에이전트), 프론트엔드, 비전 인식, 판단 알고리즘, RAG를 4명이 어떻게 나눌지.
2. **서비스 함수 시그니처**: `PatientDataPort`의 함수 목록과 반환 타입을 API 스키마와 함께 첫 시간에 확정할지.
3. **REST 방식을 택하는 경우**: 에이전트 전용 엔드포인트를 `/api/internal/...` 같은 별도 경로로 구분할지.
4. **교체 중단 시점**: 마감 2시간 전으로 할지.
