# 하루 파일럿 설계 전 검토 (팀 제안안)

**상태**: 팀 제안안 — 팀 회의에서 확정 전 · **작성일**: 2026-11-27
**관련 문서**: [기획안](proposal.md) · [서비스 워크플로우](workflow.md) · [섭취량 추정 가능성 검토](research/intake-estimation-feasibility.md)

이 문서는 시스템 프로토콜과 엔티티를 설계하기 전에 검토한 항목과 제안을 정리한 것이다. 아래 내용은 모두 **팀에 제안하는 안**이며 팀의 결정이 아니다.

## 1. 파일럿의 목적과 전제

- **목적**: 비전 인식으로 식사 섭취량을 추정하고, 그 결과를 바탕으로 처방을 추천하는 흐름이 **가능한지 검증**한다. 높은 정확도는 요구하지 않는다.
- **구현 기간**: 하루(8시간).
- **배식 가정**: 모든 대상 환자는 같은 일반식을 메뉴별 표준 배식량으로 받는다. 메뉴별 배식량과 식판 내 칸 위치는 제공된다.

## 2. 하루가 끝날 때의 완료 기준 (제안)

다음 흐름이 처음부터 끝까지 동작한다.

```
사진 업로드 → 섭취량 분석 → 섭취 부족 알림(또는 조회) → 처방 추천 → 의사의 처방 확정
```

## 3. 화면 구성 (제안)

| # | 화면 | 사용자 | 기기 | 우선순위 |
| --- | --- | --- | --- | --- |
| 1 | 기준 식전 사진 업로드 (끼니당 1장) | 영양사 | 모바일 웹 | 필수 |
| 2 | 식후 사진 업로드 (환자별) | 요양보호사 | 모바일 웹 | 필수 |
| 3 | 환자별 대시보드 + 대화 — 환자를 고르면 섭취 추이·추천 카드·처방 확정(왼쪽)과 그 환자 전용 대화(오른쪽)를 나란히 표시 | 의사 | PC 웹 | 필수 |
| 4 | 시스템 처리 상태 대시보드 | 시연용 | PC 웹 | 필수 |

- 기준 식전 사진을 찍는 사람은 **영양사**로 한다 (워크플로우 문서의 "배식 담당자"를 대체).
- 처음에는 대시보드와 대화를 별도 화면으로 두었으나, 한 환자의 맥락을 함께 보도록 **한 화면의 좌우 분할**로 합쳤다. 좁은 화면에서는 위아래로 쌓인다.
- 화면 샘플: [NutriSight 화면 샘플 캔버스](https://claude.ai/artifact/CVfusiwYXDFsnKDt3tWbko) (샘플 데이터).
- 화면이 4개이므로 화면 작업이 일정의 병목이다. API 계약을 먼저 확정해 디자인·화면·백엔드를 동시에 진행해야 한다.

## 4. 기술 구성 (제안)

| 영역 | 제안 | 이유 |
| --- | --- | --- |
| 백엔드 | **FastAPI** | 화면 4개가 공유하는 HTTP API. 분석·영양·추천 모듈은 파이썬 함수로 연결한다. |
| 화면 | **Claude Design으로 디자인 → React 웹 구현** | 웹/백엔드를 직접 구현할 수 있는 팀원이 있다. 빌드한 정적 파일을 FastAPI가 함께 제공해 접속 주소를 하나로 유지한다 (개발 중에는 Vite 프록시). |
| 저장 | **SQLite + 로컬 파일 폴더** | 설치 없이 대표자 PC 한 대에서 실행. 사진은 폴더에, 경로는 DB에 둔다. |
| 섭취량 추정 | **VLM** (기준 식전·식후 사진 비교) | 분석 모듈이 프롬프트와 출력 스키마로 줄어든다. 각도 차이, 양념 자국, 국을 모델이 함께 판단한다. |
| 처방 추천 | **LangChain `create_agent` + Claude** | 도구 호출 루프와 대화 기록을 직접 만들 필요가 없다. |
| 추천 근거 자료(RAG) | **공개 가이드라인으로 시작** | 처방 데이터가 확정되기 전이므로 공개 자료로 시작하고, 확정되면 문서만 교체한다. |

### 4-1. 섭취량 추정 (VLM)

- 입력: 끼니의 기준 식전 사진, 환자의 식후 사진, 칸 배치(칸 위치 → 메뉴 이름, 표준 배식량).
- 출력(칸별): 섭취 비율(10% 단위), 확신도, 판단 불가 여부, 사진 품질 문제.
- 출력 필드는 기존 계약(`intake_fraction_est`, `estimate_basis`, `status`)을 따른다. `estimate_basis = "vlm"`.
- 정확도 평가는 저울로 잰 모의 식판 몇 개로 대략의 오차를 보고하는 수준으로 한다. 가능하면 팀원 눈대중과 비교한다.
- OpenCV 면적비는 범위에서 뺀다 (기획안 대비 변경).
- 파일럿은 모의 식판만 쓰므로 외부 API로 사진을 보내도 된다. 실제 운영에서는 별도 검토가 필요하다.

### 4-2. 처방 추천 에이전트

- `langgraph.prebuilt.create_react_agent`는 LangGraph v1에서 권장되지 않게 되었고, 후속 함수 **`langchain.agents.create_agent`**를 쓴다.
- 대시보드 영역과 대화 영역이 **같은 도구**를 공유한다 (후보: 환자 섭취 요약 조회, 가이드라인 검색, 처방 초안 작성).
  - 대시보드: 경고가 생기면 에이전트를 한 번 실행해 구조화된 추천 카드를 저장·표시한다.
  - 대화: 같은 에이전트로 의사가 자유롭게 질문하고, 대화에서 추천 카드를 고칠 수 있다.
- **대화는 환자별 독립 스레드**로 둔다. 환자 간에 맥락이 섞일 필요가 없으므로 체크포인터의 `thread_id`를 환자(필요하면 환자 + 대화 회차) 단위로 잡고, 도구는 선택한 환자 ID로만 조회하게 제한한다. "새 대화"는 같은 환자의 새 스레드를 연다.
- **처방 확정은 의사 승인으로만** 한다. 에이전트는 초안까지만 만든다.
- 오전에 먼저 검증할 기술 위험:
  - Claude Opus 5.5는 강제 도구 호출(`tool_choice` `any`/`tool`)을 거부한다. 구조화 출력은 `ProviderStrategy`를 우선 검토하고, `ToolStrategy`가 강제 호출을 쓰는지 확인한다.
  - Opus 5.5는 대화를 이어갈 때 thinking 블록을 그대로 되돌려 보내야 한다. `langchain-anthropic`이 이를 처리하는지 짧은 대화로 확인한다.

## 5. 섭취 부족 경고 규칙 (제안)

### 근거 기준

**하루 필요량**

| 기준 | 에너지 | 단백질 |
| --- | --- | --- |
| [2025 한국인 영양소 섭취기준](https://www.mohw.go.kr/board.es?act=view&bid=0027&list_no=1488441&mid=a10503000000) (보건복지부) | 필요추정량: 남 65~74세 2,000 / 75세 이상 1,900 kcal, 여 1,600 / 1,500 kcal | 권장섭취량: 남 60 g, 여 50 g |
| [ESPEN 노인 임상영양 가이드라인](https://www.espen.org/files/ESPEN-Guidelines/ESPEN%5Fpractical%5Fguideline%5FClinical%5Fnutrition%5Fand%5Fhydration%5Fin%5Fgeriatrics.pdf) | 30 kcal/kg/일 (개인별 조정) | 1.0 g/kg/일 이상 (질환 시 1.2~1.5 g/kg) |

**섭취 부족 판단 (기간 × 비율)**

| 기준 | 내용 |
| --- | --- |
| [AND/ASPEN 2012](https://aspenjournals.onlinelibrary.wiley.com/doi/full/10.1177/0148607112440285) 급성 질환 맥락 | 필요 에너지 75% 미만이 7일 초과 → 중등도, 50% 이하가 5일 이상 → 중증 |
| AND/ASPEN 2012 만성 질환 맥락 | 75% 미만이 1개월 이상 |
| [GLIM](https://www.clinicalnutritionjournal.com/article/S0261-5614(25)00086-X/pdf) | 필요 에너지 50% 이하가 1주 초과, 또는 어떤 감소든 2주 초과 |

이 기준들은 영양불량 진단의 **한 요소**이며 섭취량만으로는 진단이 아니다. 시스템은 "영양불량"이 아니라 **"섭취 부족 위험"**으로 표시하고 판단은 의사에게 맡긴다.

### 제안 규칙

- **분모**: 환자별 하루 필요량. 체중이 있으면 ESPEN(30 kcal/kg, 1.0 g/kg), 없으면 한국인 영양소 섭취기준(성별·연령). 배식 계획 급여량 대비 섭취율은 참고값으로 함께 표시한다.
- **주의**: 최근 7일 평균 에너지 또는 단백질 섭취가 필요량의 **75% 미만**.
- **경고**: 에너지 또는 단백질 섭취가 필요량의 **50% 이하인 날이 연속 5일 이상**.
- **대상 영양소**: 에너지, 단백질. 나트륨은 상한 쪽 기준(만성질환위험감소섭취량)이라 부족 경고에서 제외한다. 따라서 국은 건더기 기준 판단으로 충분하다.
- 임계값과 기간은 설정값으로 둔다. 미기록 끼니는 평균에서 제외하고 미기록 수를 함께 표시한다.
- 워크플로우 문서의 "배식 계획 급여량 대비" 기준을 이 안으로 대체한다.

## 6. 데이터 (제안)

- **입력 데이터**: 팀이 실물 식판과 음식으로 기준 식전·식후 사진을 직접 촬영하고 저울로 잰다. 칸 좌표(칸 위치 → 메뉴)는 이 식판에 맞춰 정하고, 영양성분은 식약처 데이터로 채운다.
- **모의 이력**: 가상 환자 몇 명의 1~2주 섭취 기록을 미리 넣어 두고, 시연에서 업로드한 끼니가 그 뒤에 이어지게 한다. 주의·경고·추천·처방 흐름을 모두 보여주기 위함이다. 엔티티에 모의 데이터와 실제 업로드를 구분하는 표시가 필요하다.

## 7. 모듈 경계 (제안, 담당자 배정은 팀 회의)

| 모듈 | 내용 | 계약 |
| --- | --- | --- |
| 섭취 추정 | VLM 프롬프트·출력 스키마, 저울 실측 평가 | `추정(기준 사진, 식후 사진, 칸 배치) → 칸별 섭취 비율·확신도·상태` |
| 영양 계산·경고 | 영양성분 표, 필요량 계산, 경고 규칙, 모의 이력 시드 | `섭취 비율 → 영양소 섭취량`, `환자 이력 → 주의/경고` |
| 백엔드·화면 | FastAPI, SQLite, React 화면 4개 | HTTP API, 처리 상태 |
| 처방 추천 에이전트 | RAG 문서, `create_agent`, 도구, 대화 | `추천(환자 ID) → 추천 처방·근거`, 대화 응답 |

섭취 추정, 영양 계산·경고, 처방 추천 모듈은 파이썬 함수 계약으로 백엔드에 연결하고, 백엔드만 HTTP API를 노출한다. 화면 작업량이 가장 크므로, 먼저 끝난 담당자가 화면 일부를 맡는 방안을 함께 검토한다.

## 8. 엔티티·프로토콜 설계로 넘어가며 드러난 필요 항목

이번 검토로 엔티티에 들어가야 할 것이 드러났다. 설계 시 반영한다.

- **환자**: 성별, 나이, 체중(선택), 일반식 여부.
- **배식 계획**: 날짜·끼니, 칸 위치 → 메뉴, 메뉴별 표준 배식량과 영양성분.
- **사진**: 종류(기준 식전 / 식후), 업로더 역할, 환자(식후만), 날짜·끼니, **처리 상태**(업로드됨 → 분석 중 → 완료 / 실패 / 판단 불가).
- **칸별 섭취 추정**: 섭취 비율, 확신도, `estimate_basis`, `status`.
- **섭취 기록·경고**: 일별 집계, 주의/경고 수준, 근거 기간, 미기록 수.
- **처방 추천**: 추천 처방, 근거 문서, 생성 시점, 연결된 경고.
- **처방**: 의사, 처방 내용, 시점, 원래 추천과의 연결, 상태(초안 / 확정).
- **대화 스레드**: 환자, 스레드 ID(체크포인터 `thread_id`), 생성 시점. 환자별로 독립.
- **데이터 출처 표시**: 모의 데이터 / 실제 업로드.

## 9. 남은 열린 문제

1. **분업과 담당자 배정** — 팀 회의에서 정한다.
2. **처방 데이터** — RAG에 넣을 처방 데이터는 아직 탐색 중이다. 공개 가이드라인으로 시작하고 확정되면 교체한다.
3. **처방 유형과 기록 필드** — 추천·처방 엔티티의 처방 유형 목록(강화식, ONS, 식사 형태 변경, 영양 상담 의뢰 등)과 필드를 정해야 한다.
4. **VLM 모델과 호출 방식** — 섭취 추정에 쓸 VLM과, 결과를 안정화하는 반복 호출 여부를 정해야 한다.
5. **기술 위험 검증** — `create_agent` + Claude Opus 5.5의 구조화 출력과 thinking 블록 처리를 오전에 확인해야 한다.
